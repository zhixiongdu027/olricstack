# Watchdog State And Protocol Review

> **Pre-cutover document.** Sections that describe the data plane as a
> StatefulSet with PVCs reflect the older architecture. The control plane
> (Watchdog ↔ node heartbeats, lease/epoch/generation, bookworm) is
> unchanged. The data-plane workload is now a Deployment whose Pods carry
> `olric-node` + `olric-sidecar` containers with no PVCs — see
> [Sidecar Oplog Cutover](sidecar-oplog-cutover.md).

This document reviews the current Watchdog, Olric node, and Kubernetes interaction model before production hardening.

## Current Model

The current control loop has three inputs:

- `OlricStack` spec: desired state for this stack.
- Node heartbeat stream: primary runtime membership signal.
- Kubernetes Pod observation: secondary runtime signal from the local stack's Pods.

The current outputs are:

- Kubernetes resources reconciled by Watchdog: Olric StatefulSet and headless Service.
- Topology pushed to nodes: structured `members`, monotonic `epoch`, topology lease, Watchdog identity, generation, and role.
- Periodic bookworm snapshots: full topology pushed even without topology changes.

The intended authority order is:

- Desired capacity and pod template come from `OlricStack.spec`.
- Membership comes from node heartbeat.
- Kubernetes Pod state can exclude or qualify existing heartbeating nodes, but must not create membership by itself.

## Invariants

These invariants should be enforced before production:

- A node is not routable until it has sent a valid heartbeat.
- A Pod observation cannot create cluster membership.
- A terminal Pod observation can remove or suppress a heartbeating node.
- A topology update is always a full snapshot, not a patch.
- `epoch` must be monotonic per stack.
- Nodes must ignore stale epochs and treat same-epoch bookworm snapshots as anti-entropy refreshes.
- Watchdog must never require inbound connectivity to nodes.
- Watchdog reconciliation must be idempotent.
- The system must tolerate duplicate heartbeats, duplicate streams, and delayed packets.

## Protocol Concerns

The initial prototype protocol was minimal:

```proto
rpc SubscribeTopology(stream Heartbeat) returns (stream TopologyResponse);

message Heartbeat {
  string stack_id = 1;
  string pod_name = 2;
  string pod_ip = 3;
  int64 observed_epoch = 4;
}

message TopologyResponse {
  repeated string pod_ips = 1;
  int64 epoch = 2;
}
```

That was enough for bootstrap, but insufficient for production. The current protocol has moved to a v2 envelope shape with structured members, node identity, incarnation, role, generation, and lease validity.

Missing heartbeat fields:

- `node_id`: stable identity across IP changes and pod restarts. `pod_ip` alone is not a safe identity.
- `incarnation`: restart generation generated by the node at boot. This prevents stale streams from older processes winning.
- `role`: candidate, joining, ready, draining, leaving.
- `protocol_version`: for rolling upgrades.
- `build/version`: useful for compatibility gating.
- `started_at` or boot UUID: distinguishes old process from new process with same Pod name.
- `zone` or failure domain: needed for topology-aware placement later.

Missing topology response fields:

- `members`: structured member entries, not just IPs.
- `node_id`, `pod_name`, `pod_ip`, `state`, `incarnation`, `last_seen`.
- `reason`: event, bookworm, prune, reconcile, manual.
- `valid_until` or lease deadline: lets nodes reason about staleness.
- `min_protocol_version` or feature gates.

Current protocol shape:

```proto
message Heartbeat {
  string stack_id = 1;
  string node_id = 2;
  string pod_name = 3;
  string pod_ip = 4;
  int64 incarnation = 5;
  int64 observed_epoch = 6;
  NodeState state = 7;
  string protocol_version = 8;
}

message Member {
  string node_id = 1;
  string pod_name = 2;
  string pod_ip = 3;
  int64 incarnation = 4;
  NodeState state = 5;
}

message TopologyResponse {
  string stack_id = 1;
  repeated Member members = 2;
  int64 epoch = 3;
  TopologyReason reason = 4;
  int64 valid_until_unix_ms = 5;
  string watchdog_id = 6;
  int64 watchdog_generation = 7;
  WatchdogRole watchdog_role = 8;
}
```

## State Machine Concerns

The current `ClusterState` is deliberately simple. Production needs explicit node lifecycle states:

- `Unknown`: observed by Kubernetes but no heartbeat yet.
- `Joining`: heartbeat received but not yet admitted.
- `Ready`: heartbeating, Kubernetes not terminal, included in topology.
- `Suspect`: heartbeat overdue but not expired.
- `Unreachable`: heartbeat expired, excluded from topology.
- `Draining`: desired removal or scale-down, should not receive new ownership.
- `Leaving`: node acknowledged departure.
- `Removed`: forgotten after retention.

Important distinction:

- Reconciliation creates or deletes Pods.
- Membership admission decides whether nodes are in topology.
- Data ownership transfer should happen only around explicit lifecycle transitions.

Current implementation directly changes topology on heartbeat and terminal Pod observations. This is acceptable for the prototype but too abrupt for production because Olric ownership movement can require staged transitions.

## Timing Model

Recommended timeouts should be explicit and related:

- `heartbeat_interval`: node sends heartbeat every N seconds.
- `suspect_after`: Watchdog marks node suspect after missing M heartbeats.
- `expire_after`: Watchdog excludes node after missing K heartbeats.
- `bookworm_interval`: Watchdog sends anti-entropy topology snapshots.
- `reconcile_interval`: Watchdog reconciles Kubernetes desired resources.
- `pod_observation_interval`: Watchdog refreshes Kubernetes Pod observations.

Suggested relation:

- `suspect_after >= 2 * heartbeat_interval`
- `expire_after >= 3 * heartbeat_interval`
- `bookworm_interval <= expire_after / 2`
- `reconcile_interval` should not be tied to heartbeat frequency.

The current code has `SuspectAfter`, `ExpireAfter`, `ReapInterval`, `BookwormInterval`, `TopologyLeaseTTL`, and `WatchdogReconcileInterval`.

## Extreme Scenario Walkthroughs

### Node starts before Pod IP is visible in Kubernetes

Expected behavior:

- Node heartbeats first.
- Watchdog admits membership from heartbeat.
- Later Pod observation enriches state.

Current behavior:

- Works. Pod observation is not required to create membership.

Risk:

- If heartbeat spoofs stack ID and IP, it can join unless identity is authenticated.

Required hardening:

- mTLS or token-based node authentication.
- Validate Pod name/IP against Kubernetes once observation arrives.

### Kubernetes sees Pod but node process is not ready

Expected behavior:

- Pod observation alone must not add member.

Current behavior:

- Works. Pod-only observation does not create membership.

### Watchdog loses Kubernetes API temporarily

Expected behavior:

- Existing heartbeat-based topology continues.
- Reconcile errors should not stop topology stream service.
- Pod observation should be stale but not authoritative.

Current behavior:

- Watchdog controller `Run` returns on reconcile error, which stops the local controller goroutine.

Required hardening:

- Reconcile loop should log and continue with backoff.
- Expose degraded status.

### Watchdog restarts

Expected behavior:

- Nodes reconnect after stream breaks.
- Watchdog reconstructs membership from new heartbeats.
- Epoch behavior should be well-defined.

Current behavior:

- In-memory state is lost.
- Epoch resets to zero.
- Nodes will reconnect and rebuild topology.

Risk:

- Epoch reset can make stale node logic ambiguous.

Required hardening:

- Persist stack epoch in `OlricStack.status` or a ConfigMap/Lease.
- Include Watchdog generation in topology.

### Duplicate stream from same Pod

Expected behavior:

- Newer incarnation wins.
- Older stream should be rejected or ignored.

Current behavior:

- Subscriber map is keyed by Pod IP; last stream wins.
- No incarnation check.

Required hardening:

- Add `node_id` and `incarnation`.
- Reject lower incarnation.
- Close stale stream when newer stream registers.

### Pod IP reuse

Expected behavior:

- New process must not inherit old membership identity.

Current behavior:

- Pod IP is identity, so IP reuse is unsafe.

Required hardening:

- Use stable `node_id` plus incarnation.
- Treat IP as transport address, not identity.

### Network partition between node and Watchdog

Expected behavior:

- Node should eventually consider topology lease stale.
- Watchdog marks node suspect, then unreachable, then excludes.
- Node must stop accepting writes or downgrade to read-only when the topology lease expires.
- Node must continue trying to flush already accepted dirty data if MySQL is reachable.

Current behavior:

- Watchdog marks node `SUSPECT` after `SuspectAfter` and removes it after `ExpireAfter`.
- Topology v2 includes `valid_until_unix_ms`.
- Node subscriber records epochs but does not yet enforce lease expiry locally.

Required hardening:

- Add node-side topology lease watchdog.
- On lease expiry, reject new writes with 503 or read-only mode.
- Continue write-behind drain for accepted dirty entries.
- Report local lease state in heartbeat.

### Kubernetes scales down StatefulSet

Expected behavior:

- Watchdog observes desired replica reduction.
- Target nodes enter draining before removal.
- Topology changes after safe handoff.

Current behavior:

- StatefulSet replicas change directly.
- Membership removal depends on heartbeat ending or terminal Pod observation.

Required hardening:

- Add drain protocol.
- Prefer ordinal-aware scale-down.
- Push topology state `Draining` before exclusion.

### MySQL overload or dirty queue full

Expected behavior:

- Node heartbeat should report pressure.
- Watchdog topology may mark node degraded.

Current behavior:

- Store returns `ErrQueueFull`, but heartbeat does not report pressure.

Required hardening:

- Add node health fields to heartbeat: queue depth, write errors, MySQL status.
- Watchdog excludes or deprioritizes unhealthy nodes based on policy.

## V2 Timing And Interaction Model

### Primary Watchdog Happy Path

1. Watchdog starts as `PRIMARY` with `watchdog_id` and `watchdog_generation`.
2. Node starts with stable `node_id` and boot `incarnation`.
3. Node opens `Watch` and sends `Heartbeat`.
4. Primary validates identity fields and applies heartbeat to `ClusterState`.
5. `ClusterState` increments `epoch` if membership-visible data changed.
6. Primary pushes `TopologyEnvelope` with full `members`, `epoch`, `valid_until`, `watchdog_id`, `watchdog_generation`, and `watchdog_role`.
7. Node applies envelope only if generation/epoch are acceptable and lease is valid.
8. Bookworm periodically pushes the same full snapshot even if epoch is unchanged.

### Standby Watchdog Behavior

Standby must not own runtime membership.

Expected behavior:

- Standby may answer discovery with role metadata.
- Standby must not admit heartbeats into topology.
- Standby must not reconcile active topology decisions.
- Standby may keep warm cache from Kubernetes and, later, shared persisted status.

Current behavior:

- Static `WATCHDOG_ROLE=standby` disables topology ownership.
- Static role is not real failover.

Required hardening:

- Add Kubernetes Lease election per stack.
- Only current lease holder is primary.
- Watchdog generation must increase on primary transition.
- Nodes must reject stale primary generations.
- Standby should redirect or return role metadata so nodes reconnect to primary service endpoint.

## Failure Matrix

### Intermittent Node-to-Watchdog Network

Symptoms:

- Heartbeats arrive with jitter.
- Bookworm snapshots may be delayed.
- Node still serves traffic locally.

Expected behavior:

- Short jitter below `SuspectAfter` causes no topology change.
- Missing heartbeats beyond `SuspectAfter` marks node `SUSPECT`.
- Missing heartbeats beyond `ExpireAfter` removes node from topology.
- Node must stop accepting writes when its local `valid_until` expires.

Data concern:

- The node may have dirty writes accepted before lease expiry.
- Those writes must be flushed even if node is no longer in topology.

Required hardening:

- Node-local lease watchdog.
- Separate serving state from flush state: `Serving=false`, `FlushAllowed=true`.
- Heartbeat includes dirty queue depth and oldest dirty age.

### One-Way Network Failure

Case A: node can send heartbeat but cannot receive topology.

- Watchdog thinks node is alive.
- Node topology lease expires locally.
- Node must stop serving writes despite still heartbeating.

Case B: node can receive but cannot send heartbeat.

- Watchdog marks node suspect/expired.
- Node may keep receiving old stream data until transport fails.
- Node must obey `valid_until`, not just stream liveness.

Required hardening:

- Treat topology lease as authority on the node.
- Heartbeat stream liveness alone is insufficient.

### Watchdog-to-Kubernetes API Failure

Expected behavior:

- Heartbeat-based topology continues.
- Pod observations become stale and must not dominate.
- Reconciliation should retry with backoff and expose degraded status.

Current behavior:

- Controller loop can return on reconcile error.

Required hardening:

- Never terminate topology service due to Kubernetes API errors.
- Controller Run loop should log, backoff, and continue.
- Add status condition: `KubernetesObservationDegraded`.

### Kubernetes Network Plugin Failure

Potential symptoms:

- Pod IP changes or disappears.
- Pod remains Running but network unreachable.
- Service DNS works but data plane traffic fails.
- Watchdog may still receive heartbeats from some nodes.

Expected behavior:

- Heartbeat is primary; absence of heartbeat drives suspect/removal.
- Pod Running alone must not keep membership alive.
- If Pod IP changes, node must heartbeat with same `node_id`, higher `incarnation` or same process identity if safe.

Data concern:

- Network plugin failure may isolate node from MySQL too.
- Dirty queue may grow and eventually reject writes.

Required hardening:

- Heartbeat includes MySQL reachability and dirty queue pressure.
- Watchdog marks node `DRAINING` or `SUSPECT` based on pressure.
- Node refuses new writes when queue crosses high-watermark.

### Pod Abruptly Dies

Expected behavior:

- Heartbeats stop immediately.
- Kubernetes may report terminal state before heartbeat TTL.
- If terminal observation arrives, Watchdog excludes the node before `ExpireAfter`.
- If Kubernetes observation is delayed, Watchdog excludes after `ExpireAfter`.

Dirty data concern:

- In-memory dirty queue is lost on abrupt process death.
- Current write-behind design can lose acknowledged writes.

This is not production-safe if `Store` acknowledges before data is durable.

Required hardening options:

- Use a local WAL before acknowledging writes.
- Or only acknowledge after MySQL flush for strong durability mode.
- Or expose write-behind as explicitly lossy cache mode with documented semantics.
- Store per-entry sequence numbers to avoid stale flush ordering.

### Node Process Hangs But Pod Remains Running

Expected behavior:

- No heartbeat means Watchdog marks suspect then removes.
- Pod observation Running must not preserve membership.

Dirty data concern:

- Dirty queue may be stuck in memory.
- MySQL flush thread may be hung.

Required hardening:

- Liveness probe should kill hung process.
- Heartbeat should include flush worker health.
- Watchdog should not treat Kubernetes Ready as sufficient.

### MySQL Slow Or Unavailable

Current store behavior:

- `Store` enqueues dirty data.
- Background flush writes batched upserts.
- Queue full returns `ErrQueueFull`.
- Flush error is stored as worker error but does not currently affect node heartbeat or serving state.

Risk:

- Writes accepted into memory can be lost if node dies before flush.
- Repeated flush failures can leave dirty data in memory indefinitely.
- Current `flushPending` drops the pending map after a failed flush because caller resets `pending`.

Critical bug:

- On `flushPending` error, entries are not retained for retry.
- This can lose dirty writes even without process death.

Required hardening:

- `flushPending` must return error.
- Pending entries must remain queued until successful flush or durable WAL handoff.
- Implement retry with backoff and max dirty age.
- Add queue high/low watermarks.
- Heartbeat reports `dirty_queue_depth`, `oldest_dirty_age_ms`, `last_flush_error`, `mysql_reachable`.
- Watchdog marks node `DRAINING` or removes it from write topology under sustained MySQL failure.

### MySQL Partial Batch Failure

Expected behavior:

- The node must know which entries were persisted.
- Failed entries must be retried.

Current behavior:

- GORM `CreateInBatches` returns one error for the operation.
- No per-row success accounting.

Required hardening:

- Use transaction boundaries and retry whole batch.
- Include monotonically increasing version per key to prevent stale overwrite.
- Consider dead-letter queue for poison values.

### Primary Watchdog Fails

Expected behavior:

- Standby wins Lease and becomes primary.
- New primary generation increases.
- Nodes reconnect or receive role change.
- Nodes reject stale envelopes from old primary.

Current behavior:

- Static primary/standby only.
- No Kubernetes Lease election.
- No persisted epoch.

Required hardening:

- Kubernetes Lease per `OlricStack`.
- Persist epoch/generation in status or durable object.
- Nodes track `(watchdog_generation, epoch)`.
- If topology lease expires during failover, nodes stop accepting writes until new primary envelope arrives.

### Split Brain Watchdogs

Expected behavior:

- Only one primary can hold the Lease.
- Nodes reject envelopes from non-holder generation.

Failure if not handled:

- Two primaries can push conflicting topology.
- Nodes may diverge membership view.

Required hardening:

- Lease-backed fencing token.
- Include Lease resourceVersion or generation in envelope.
- Nodes must prefer higher valid generation and reject lower generation.
- Primary must step down immediately when Lease renewal fails.

### Duplicate Node Streams

Expected behavior:

- Same `node_id`, higher `incarnation` wins.
- Same `node_id`, lower incarnation is ignored/rejected.
- Same incarnation duplicate stream should result in one active subscriber.

Current behavior:

- State ignores stale lower incarnation.
- Subscriber replacement is keyed by `node_id`.
- Old stream is not actively closed.

Required hardening:

- Close old subscriber channel when replaced.
- Reject same incarnation duplicate unless connection replaces prior stream deterministically.

## MySQL Write-Behind Production Contract

The storage layer must choose and expose one durability contract:

### Contract A: Durable Write-Behind

- Node writes to local WAL before ack.
- Background worker flushes WAL to MySQL.
- On restart, node replays WAL.
- Topology should not remove a node from drain workflow until WAL is empty or transferred.

### Contract B: Best-Effort Cache Write-Behind

- Node may acknowledge before durability.
- Abrupt death may lose dirty data.
- This must be documented and not marketed as durable storage.

Given the project goal says "MySQL persistent fallback", production should target Contract A.

Required protocol additions:

- Heartbeat health block:
  - `dirty_queue_depth`
  - `oldest_dirty_age_ms`
  - `last_flush_unix_ms`
  - `last_flush_error`
  - `mysql_reachable`
  - `wal_pending_bytes`
- Member state policy:
  - `READY`: can serve reads/writes.
  - `DRAINING`: no new writes, flush dirty data.
  - `SUSPECT`: no new ownership assignment.
  - `UNREACHABLE`: excluded from topology.

## Revised Priority List

Priority 0:

- Fix write-behind retry bug: failed flush must not drop pending data.
- Add node-side topology lease enforcement.
- Add Kubernetes Lease primary election and fencing generation.
- Persist epoch/generation across Watchdog failover.
- Add heartbeat health fields for MySQL/dirty queue state.

Priority 1:

- Add explicit drain workflow for scale-down and unhealthy nodes.
- Add WAL-backed durable write-behind.
- Add duplicate stream replacement/closure.
- Make Watchdog reconcile loop non-fatal with backoff.
- Add metrics for stream state, epoch, lease expiry, dirty queue, flush failures.

Priority 2:

- Add chaos e2e:
  - packet loss and delayed heartbeat
  - Watchdog primary failover
  - Kubernetes API outage
  - Pod abrupt death
  - MySQL outage and recovery
  - duplicate node incarnation

## Production Priorities

Priority 0:

- Add `node_id`, `incarnation`, and structured `Member` to protocol.
- Add explicit node lifecycle states.
- Add topology `valid_until`.
- Make Watchdog reconcile errors non-fatal with backoff.
- Persist or externalize epoch/generation.

Priority 1:

- Add Pod identity validation: heartbeat `pod_name` and `pod_ip` must match Kubernetes observation.
- Add duplicate stream handling.
- Add suspect state before removal.
- Add status updates to `OlricStack.status`.
- Add metrics for heartbeats, topology epoch, subscriber count, reaper removals, reconcile errors.

Priority 2:

- Add graceful drain for scale-down and rolling upgrade.
- Add mTLS or service account token authentication.
- Add integration tests with fake Kubernetes watch events.
- Add chaos e2e: Watchdog restart, API outage, stream partition, duplicate node.

## Recommended Next Step

The next implementation step should be protocol v2:

- Add Kubernetes Lease-based primary election.
- Persist epoch/generation across Watchdog restarts.
- Harden node subscriber handling for stale Watchdog generations and expired topology leases.
- Add explicit drain and scale-down lifecycle transitions.

This should happen before adding more Kubernetes automation, because the state model is the foundation for safe reconciliation.
